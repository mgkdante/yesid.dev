Story entries can reuse a file. Paired captures put dark in `data.file` and
light in `data.variants.light`. Singles and Café Arona's light-only captures
have only `data.file`. Each file object includes its Directus UUID, editor
URLs, actual pixel dimensions, byte size and original filename. Runtime
delivery resolves those UUIDs through the committed mirror map.

Transit entries with `status: "held-map-polish"` preserve their original order
and section without a block or registered file. Add their actual captures in
a future media release; do not paste a placeholder into published content.

The 113 originals live under
`apps/web/static/images/work/<project>-20261109/`, with responsive WebP
variants generated by `scripts/lib/media-variants.ts` (240, 600, 1200 and
1600 pixels, capped at source width and retained only when smaller).
The asset manifest records each original's SHA-256; both ID maps receive
additive entries, following the Café Arona commits c1270573 and cf362b5e.
`packages/shared/src/asset-registry.ts` defines interfaces and validators,
not the concrete project image inventory; the precedent did not modify it.

Verification used the supplied local upload bytes and Directus production
`GET /assets/<id>` responses. The scoped Build Bot token supplied by
1Password authenticated successfully but returned 403 for these assets;
unauthenticated asset GETs returned the images. A temporary driver called the
existing `mirrorAsset` function from `scripts/mirror-asset.ts` with public
GETs, previewed each file, compared its SHA-256 to the local upload and manifest,
then applied with that exact reviewed SHA-256. Apply independently re-fetched
and checked the bytes. No production uploads, item edits or sync pushes were
performed. This registration does not publish or replace case-study content.
